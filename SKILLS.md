# UI/design conventions for this repo

Distilled from work on `riscv_simulator.html`; apply the same instincts to the other visualization pages here.

- **Reuse existing patterns instead of inventing new ones.** A new panel/control should look and behave like its closest sibling already in the page (e.g. a new value column gets the same signed/unsigned toggle Registers and Memory already use) rather than a bespoke widget.
- **Show a value in more than one form when its format is ambiguous** — hex alongside signed/unsigned decimal, not just one. Make it toggleable rather than picking one and hiding the rest.
- **Prefer copy that stays true automatically over copy that enumerates specifics.** A message naming exact items (panel names, counts) goes stale the next time something is added; phrase it generically unless the specifics are the point.
- **Never show a value before it's meaningful.** If something reads from state that isn't valid yet (a register before its prologue runs, a result before a compile finishes), show a clear "not ready yet" state instead of whatever garbage happens to be there.
- **Debuggability is a first-class feature here.** Surfacing what the simulator is actually doing (memory layout, variable locations, live values) is consistently the kind of addition that's wanted — lean toward more visibility, not less.
- **Write UI copy for the actual audience: a mature CS/CompArch student, not a first-time computer user.** Don't explain what a checkbox or a panel chip does — that's obvious once seen. Don't spell out that an assembler rejects invalid syntax, or narrate a control's past behavior ("previously two words per row, now one") — state the current fact once, plainly. If a table conveys the same facts a paragraph does, prefer the table; it's denser and matches how the rest of these docs are already structured.
- **A UI element irrelevant to the current mode should disappear, not apologize.** A panel/control with nothing to show in the current context (e.g. a C-only panel while in assembly mode) should hide itself, not stay visible showing an explanatory placeholder.
- **Prevent an invalid state instead of just handling it.** Two checkboxes that must not both end up off (or an analogous either/or control) should refuse the toggle that would leave neither on, rather than tolerating the state and coping with it elsewhere.
- **Don't scatter the same explanation at every place it might apply.** State a cross-cutting fact (e.g. "this needs a local server") once, prominently, and point back to it elsewhere — not a full re-explanation every time it's relevant. Docs written across many incremental sessions tend to accumulate exactly this kind of repetition; a periodic re-read for redundancy is worth it.
